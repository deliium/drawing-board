# Verify follow-ups for authoritative boardRev

**Date:** 2026-09-08 20:58
**Files:** internal/db/board.go, internal/ws/handler_test.go, internal/httpapi/handlers.go, web/src/services/recognizeGate.ts, web/src/pages/BoardPage.vue, web/tests/unit/board-revision.spec.ts, README.md
**Severity:** low

## Problem

`/aif-verify` on authoritative board operations flagged non-blocking gaps: deferred SQLite txs instead of IMMEDIATE-style reserved locks, missing WS handler protocol tests, no recognize-discard unit coverage, REST delete bypassing `boardRev`, and README debug table omitting clear.

## Root Cause

Implementation prioritized store-level correctness and UI wiring; locking upgrade, transport-layer tests, and the legacy REST delete wrapper were left as follow-ups after the main plan tasks.

## Solution

- Upgrade `beginImmediate` with a no-op `UPDATE … WHERE 0` to take a reserved write lock (IMMEDIATE semantics) and log `[FIX][db.beginImmediate]`.
- Add WS handler tests for `stale_board`, clear ack/echo, and `op_cancelled` after tombstone.
- Extract `shouldAcceptRecognizeResponse` and cover discard cases in Vitest; BoardPage uses the helper.
- Route REST `DeleteStroke` through `ApplyStrokeDelete` so scripts bump `boardRev` (409 on stale).
- Document clear in the `[ws.Handle]` README debug row.

## Prevention

- When a plan requires `BEGIN IMMEDIATE`, verify the lock upgrade path in code review—not only transactional correctness.
- Prefer at least one WS-handler test when introducing new WS message types/codes, even if store tests cover semantics.
- Keep thin REST wrappers on the same revision-gated store helpers as WS to avoid silent desync.
- After protocol docs updates, grep README debug/operator tables for new message types.
